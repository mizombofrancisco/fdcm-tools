OctopusFile 2.0 (LTS)

OctopusFile 2.0 is the official long-term support (LTS) version. 2.0.0 was released on 21 November 2026; it is supported until 21 November 2028. The current version is shown at the bottom of every page of this website.

The LTS policy#

Support2 years from the release of 2.0.0: 2.0.x versions with bug and security fixes only — no new features, no API changes
APIno breaking change in the whole 2.x line; anything deprecated in 2.x is removed only in 3.0. A test (ApiSignatureTest) compares every public type, constructor, method and field with the frozen list api/octopusfile-api.txt, so a change cannot slip into a 2.0.x by accident
JavaJava 17 and newer; tested on Windows, Linux and macOS by the CI
Formatseverything written by 2.0 (vault, encrypted files, snapshot repositories, saved index) stays readable by every later version
Dependenciesnone
Branchesnew features continue on main (2.1, 2.2…); fixes for 2.0 go to the lts/2.0 branch, created with 2.0.0

Migrating from 1.x#

Code that compiled on 1.4 without removal warnings needs only the renames below. To find the uses, compile against 1.4 with -Xlint:removal.

Removed (deprecated since 1.4):

RemovedUse instead
FileManager, OctopusFile.getFileManager()the OctopusFile facade (copy, move, delete, write) or java.nio.file.Files; rename(a, b) → move(a).to(b). Note: FileManager.move/rename replaced an existing target, move(a).to(b) refuses it (use Files.move(a, b, REPLACE_EXISTING) to keep the old behaviour)
DirectoryManager, getDirectoryManager()OctopusFile.list(...), createDirectory(...) or Files; deleteDirectoryRecursively(p) → TreeUtils.deleteRecursively(p) (modules.utils; does nothing when p does not exist, as before)
BatchOperations, getBatchOperations()a loop, or TransferManager for long work with progress and cancel
AsyncOperations, getAsyncOperations()CompletableFuture or TransferManager

Renamed (the old names were the same as java.io classes):

1.x2.0
modules.reading.FileReadermodules.reading.WholeFileReader
modules.reading.BufferedReadermodules.reading.LineReader
modules.writing.FileWritermodules.writing.WholeFileWriter
modules.writing.BufferedWritermodules.writing.LineWriter

Constructors with internal types (NIO2FileSystem, FileValidator, ContentCache, …) are no longer public in FileCopier, FileMover, FileRenamer, FileDeleter, FileWatcher, WatchService and the readers and writers. Use the constructor without those arguments. The options they gave are now public on their own: LineReader(path, charset), LineWriter(path, append, charset), CsvReader(delimiter), CsvWriter(delimiter).

Errors (2.0.0-beta.1, the rule for the whole 2.x line): the OctopusFile facade throws OctopusFileException (unchecked); every module declares IOException — see Errors. The modules manipulation, reading, writing and monitoring threw OctopusFileException in 1.x: their methods now declare throws IOException, so code that calls them must catch it or declare it. LineReader.lines() throws UncheckedIOException inside the stream, like BufferedReader.lines().

Watch out — it still compiles: a catch (OctopusFileException e) around a module class (for example new FileMover().move(a, b)) compiles in 2.x when the method already declares IOException, but it no longer catches anything: the error now arrives as an IOException. Search your code for catch (OctopusFileException and, where the try calls a module class instead of the facade, catch IOException (or both: catch (IOException | OctopusFileException e)). For example, moving a folder to another drive gives DirectoryNotEmptyException; code that fell back to "copy, then delete" on OctopusFileException must now do it on that exception.

Long operations (2.0.0-beta.1): TransferManager runs copies, moves, snapshots, restores, cloud push and pull, content search, indexing and duplicate scans in one queue. Each call returns a Transfer with progress, cancel() and, when it ends, getResult(). Code that ran these on its own threads in 1.x can keep doing so (the module classes still work on their own) or move to the queue.

Checklist#

  1. Compile your code against 1.4.1 with -Xlint:removal and replace every use it reports (tables above).
  2. Switch to Java 17 or newer and to the 2.0 JAR.
  3. Rename FileReader, BufferedReader, FileWriter, BufferedWriter of com.octopusfile (imports only).
  4. Where the compiler asks, catch or declare IOException around the module classes; keep catching OctopusFileException around the OctopusFile facade.
  5. Nothing to do for your data: vaults, encrypted files, snapshot repositories, saved indexes, saved secrets and the trash written by 1.x open as they are (see below).

API freeze#

From 2.0.0-rc.1 the public API is frozen. Every public type, method and field of the exported packages is listed in api/octopusfile-api.txt, and the test suite fails if the code differs from it. Until 2.0.0 only fixes go in; during the 2 years of support, 2.x versions may only add to the API, never remove or change it. Every public element has Javadoc.
