Roadmap and guidelines for future versions

This page is for whoever builds the next versions of FileExp. It explains how versions are numbered, what every new feature must bring, how to keep users' data safe across versions, and which directions are planned.

Version numbers#

FileExp uses MAJOR.MINOR.PATCH (for example 3.7.1):

PartChanges when…Example
MAJORThe way of working changes a lot, or old data needs a one-way migration3.0.0 — the file manager became a desktop
MINORNew features, compatible with the data of the previous version3.7.0 — tabs, split view, Share nearby
PATCHFixes and small polish, no new data3.7.1 — new icon and start screen

The version lives in FileExp.VERSION (Java) and pkg.version (build.xml) — change both.

Definition of done for a new feature#

A feature is finished only when it has:

  • its logic in control / data (or the file engine), separate from the screen;
  • all its file work through the file engine, with Undo if it changes files and a timeline event;
  • all texts through I18n.tr, with the 9 translations, and build_tsv.py reporting nothing missing;
  • keyboard access (and a configurable shortcut in Shortcuts if it is a frequent action);
  • search keywords for its Settings page, if it has one;
  • automatic tests in selftest/, all passing with ant selftest;
  • a page (or section) in this documentation, in English and Portuguese, with a screenshot;
  • a line in CHANGELOG.md under "Por publicar".

Keeping users' data safe between versions#

  • Every collection file has a version field. When the shape of a document changes, migrate on read: accept the old shape, write the new one, and raise the version.
  • Never remove a field the previous version still reads, within the same MAJOR version.
  • Unknown fields must be kept when a document is saved (a newer version may have written them).
  • New settings must have a default, so an old settings.json keeps working.
  • The .bak copy is the safety net: never delete it automatically.
  • Formats that hold users' files (vault, Trash, backups) change only with a way to read the old format.

Directions for the next versions#

3.8 — Reliability and reach (released, 20 Nov 2026)#

Error log, continuous integration, accessibility and high contrast, display scaling, export and import of the settings: all done — see the version history.

3.9 — Security (released, 21 Nov 2026)#

Security review of the file engine (OctopusFile 1.3.0): Share nearby protocol 2, crash-safe vault password change, safer saved passwords and SMB on macOS — see the version history.

3.9.1 (21 Nov 2026) moved the file engine to OctopusFile 2.0.1 LTS — see the version history.

3.10 — Power features (released, 22/11/2026)#

File versions restored from the details panel, encrypted backups, folder sync between two computers with Share nearby, pause and resume in the transfers panel, content search in Office documents: all done (file engine OctopusFile 2.1.1) — see the version history.

3.11 — First run and system integration (released, 22/11/2026)#

A 10-step setup assistant with the licences, the .fexc and .fexr formats with their own icons, Settings › System and a single instance: all done — see the version history. Left for later: terms of use of Muendu Studio (the application already shows them when they exist in legal/terms-<language>.txt).

4.0 — Platform#

  • macOS package and testing.
  • An extensions API inside FileExp (actions in menus, previewers, Settings pages) — still without external libraries.
  • Revisit the window model: optionally open My Files as a normal window for people who do not want the full-screen desktop.

No automatic tests of screensInterface regressions are found by handTurn the screenshot harness into a test target that compares key screens
macOS not testedCode paths exist but are unverifiedTest on a Mac before claiming support
CHANGELOG only in PortugueseInternational usersKeep the changelog in Portuguese and the release notes of this site in both languages

Things to avoid#

  • Adding a library "just for this one thing". Write the small part needed, in the file engine, with tests.
  • Opening system windows (file choosers, alerts) — use Dialogs.
  • Long work on the JavaFX thread.
  • Network features that are on by default.
  • Deleting users' files without the Trash or a clear, explicit confirmation.
