Publicar uma versão

Uma lista de verificação passo a passo para ir do código a um instalador em que os utilizadores possam confiar.

1. Preparar#

  1. Escolha o número (ver Números de versão).
  2. Altere-o em src/ao/fileexp/FileExp.java (VERSION) e em build.xml (pkg.version). Depois compile do zero: apague build/classes (não ant clean, que também apaga dist/). VERSION é uma constante que o Java copia para as classes que a usam (Definições › Acerca, o relatório de erros): uma compilação incremental deixa lá o número antigo.
  3. Em CHANGELOG.md, mude "Por publicar" para a versão e a data, por exemplo ## 3.8.0 (02/12/2026) — Title.
  4. Execute python i18n/build_tsv.py — tem de reportar nenhuma tradução em falta.

2. Testar#

powershellant jar
ant selftest
ant selftest -Dselftest.mode=all

Ou simplesmente python ci/ci.py --mode all. Todos os testes têm de passar, e a CI tem de estar verde em Windows e Linux para o commit que publica (GitHub › Actions). Depois verifique à mão, pelo menos em inglês e em português:

  • primeira execução com uma pasta pessoal vazia (assistente de configuração, licenças, boas-vindas);
  • navegar, copiar, mudar o nome a vários, eliminar, anular, refazer;
  • pesquisar com filtros e dentro de ficheiros;
  • pré-visualização rápida de uma imagem, de um texto e de um ZIP;
  • Definições: todas as páginas abrem;
  • as novas funcionalidades desta versão.
  • python tools/scale/scale_check.py não encontra problemas em nenhuma escala, também com --lang pt (textos mais longos) (consulte Compilar e testar).

3. Empacotar#

powershellant "-Dpkg.dir=dist/package-3.8.0" package-installer

Resultados:

  • dist/package-3.8.0/image/FileExp/ — aplicação portátil;
  • dist/package-3.8.0/installer/FileExp-3.8.0.exe — instalador.

Em Linux, ant package-deb -Djavafx.jmods=/path/to/javafx-jmods-17.

4. Verificar o pacote#

  • Instalar numa conta de utilizador limpa (ou numa máquina virtual).
  • O ícone, o nome, a versão e o editor (Muendu Studio) estão corretos no instalador e em Definições › Acerca.
  • Arrancar, abrir uma pasta, pré-visualizar rapidamente um vídeo (o módulo javafx.media está incluído), sair.
  • Desinstalar: a aplicação desaparece, ~/.fileexp fica.

5. Documentação#

  • Atualizar as páginas das novas funcionalidades, em inglês e em português.
  • Atualizar as capturas de ecrã se os ecrãs mudaram.
  • Adicionar a versão ao histórico de versões (nos dois idiomas).
  • python docs/fileexp/build_site.py e abrir o site.

6. Publicar#

  • Fazer commit e a tag v3.8.0, enviar o commit e a tag (push). O workflow Release cria o Release no GitHub com o JAR e a secção da versão no CHANGELOG.md.
  • Anexar o instalador a esse Release: GitHub › Releases › a versão › Edit › arrastar FileExp-<versão>.exe de dist/package-<versão>/installer/ › Update release — ou gh release upload v<versão> dist/package-<versão>/installer/FileExp-<versão>.exe. Desde a 3.11.3 os instaladores não ficam no git (dist/package-*/ está no .gitignore): um instalador tem mais de 50 MB, e o GitHub avisa de cada ficheiro desse tamanho no push. Os ficheiros anexados a um Release podem ter até 2 GB.
  • Publicar da mesma forma a pasta da aplicação portátil (comprimida em ZIP à mão) e o .deb, se tiverem sido feitos.
  • Manter disponível o instalador da versão anterior.
