Convenções e regras

Estas regras mantêm o FileExp coerente de versão para versão. Uma alteração que quebre uma delas precisa de uma razão muito boa, escrita no changelog.

As regras inegociáveis#

  1. Sem bibliotecas externas. Apenas o JDK, o JavaFX e os pacotes do próprio projeto. Precisa de algo (JSON, HTTP, criptografia, ZIP)? Ou está no JDK, ou é escrito no motor de ficheiros.
  2. Projeto NetBeans/Ant. Sem Maven nem Gradle na aplicação. Os alvos são adicionados ao build.xml.
  3. Os dados do utilizador vão para o armazenamento NoSQL (ao.fileexp.store) — nunca para ficheiros .properties, para o registo do Windows nem para uma base de dados separada.
  4. O FXML é expandido, não reescrito. Adicione nós seguindo o padrão existente: as classes de estilo de desktop.css (o tema vem de theme-dark/theme-light na raiz), <Icon name=".." size=".."/> para ícones simbólicos, cores das variáveis CSS.
  5. Todo o texto no ecrã é traduzido. No código, I18n.tr("English text"); no FXML, o texto em inglês é traduzido por I18n.translate(root). Cada texto novo recebe uma linha em i18n/translations-*.txt.
  6. Nada se perde de surpresa. Nunca substituir (escolher um nome livre), eliminar através do Lixo, tornar as operações anuláveis, perguntar antes de tudo o que não possa ser anulado.
  7. Sem janelas do sistema. Os menus e diálogos são desenhados na cena (Overlays, Popover, Dialogs).
  8. Usar o motor de ficheiros para o trabalho com ficheiros. Não chamar java.nio.file.Files a partir dos ecrãs; se faltar algo ao motor, adicioná-lo lá, em inglês, com um teste.

Estilo de código#

  • Java 17, 4 espaços, chavetas sempre, uma classe de topo por ficheiro.
  • Nomes, comentários e registos em inglês.
  • Visibilidade de pacote por omissão; @Internal no código do motor de ficheiros que não é API pública.
  • Uma classe que só contém lógica vai para control; uma classe que contém dados do utilizador vai para data.

Regras de desempenho (aprendidas em pastas com 50 000 ficheiros)#

  • Listar pastas com Files.walkFileTree à profundidade 1 (ou com a listagem do motor): os atributos vêm com a listagem, e não com uma chamada ao disco por ficheiro.
  • Nunca criar um Tooltip por mosaico — cada um é uma janela com a sua própria cena. Criá-lo quando o rato entra.
  • Desenhar muitos mosaicos em blocos, um bloco por frame.
  • Guardar em cache o que o sistema responde lentamente (espaço livre, nomes das unidades).
  • Tudo o que possa demorar mais de ~50 ms corre em segundo plano e regressa com Platform.runLater.

Threads e JavaFX#

  • Tocar nos nós apenas na thread do JavaFX.
  • Nunca bloquear a thread do JavaFX com uma operação de ficheiros; usar a fila de transferências para tudo o que seja demorado, para que o utilizador veja o progresso e possa cancelar.
  • Dialogs usa um ciclo de eventos aninhado: não o chamar a partir de uma thread em segundo plano.

Regras de segurança#

  • As palavras-passe das contas são guardadas encriptadas (CredentialVault); as palavras-passe SMB nunca são guardadas.
  • Os nomes recebidos ou extraídos são limpos: sem .., sem caminhos absolutos, sem letras de unidade.
  • As funcionalidades de rede estão desativadas por omissão e fazem bind apenas ao endereço necessário.

Testes#

  • Cada funcionalidade vem com testes em selftest/, executados com ant selftest antes de cada build que chegue aos utilizadores.
  • Os testes usam a pasta pessoal temporária; nunca tocam na real.

Changelog#

Toda a alteração que um utilizador possa notar vai para CHANGELOG.md (em português), em "Por publicar" até a versão ser lançada.
